# 变更提案：自驱动生命系统（Autonomous Life System）

## 动机

当前架构中，Agent 的生命完全由外部驱动——用户不操作时 Agent 冻结，状态、事件、时间全部停止。
这是 NPC 模式，不是生命。真正的生命是自驱动的：世界在转，时间在流，事件在发生，Agent 在经历。
用户打开应用时看到的应该是"一个一直在活着的生命"，而不是"一个等你回来才解冻的机器"。

### 现有问题

1. **时间冻结**：`age_days` 只在 `simulate_phase` 时跳变，不随现实时间推进
2. **事件耦合**：48 种事件定义在 `cradle/events.py` 中，只在阶段模拟时触发，无时间维度
3. **无生活上下文**：同阶段的所有宝宝遇到相同的事件池，无法区分上学/不上学、有宠物/无宠物
4. **心跳是唯一的"活着"信号**：但心跳只做"想不想找人"的判断，不产生生活内容
5. **事件系统是摇篮私有的**：无法被未来的世界模块复用

## 目标

- 将 Agent 从 NPC 模式转变为自驱动生命
- 事件系统拆出为跨模块共享基础设施
- 建立世界层（规则引擎） → Agent 层（LLM 反应）的分层架构
- 实现 DES（离散事件模拟）调度器，边活边长
- 每个 Agent 每天约 10 次 LLM 调用，成本可控

## 范围

### 包含

- 共享事件系统（从 cradle/events.py 拆出，增加时间窗口 + life context 前置条件）
- DES 调度器（常驻进程，优先级队列，管理多 Agent 生命线）
- 世界层（日程模板生成 + 涌现事件掷骰）
- Agent 生活上下文（life_tags 标签系统）
- 时间模型（模拟时间 + 可配置的时间比例）
- 心跳 SSE 与调度器对接（调度器产出的事件通过 SSE 推给前端）
- 前端展示自主生命事件

### 不包含

- 世界模块（world/）的完整实现（本提案只建基础设施）
- 多 Agent 社交的自主触发（保持现有手动社交机制）
- 阶段推进的自动化（阶段推进仍由 grow_stream 驱动）
- Ray/分布式调度（当前单进程足够）

## 成功标准

- 用户离开 10 小时后回来，宝宝的状态、记忆、情绪反映了这 10 小时的生活经历
- 同阶段的两个宝宝因为 life_tags 不同，经历完全不同的事件
- 调度器能同时管理 100 个 Agent，LLM 调用不超过 1000 次/天
- 前端控制台实时展示自主生命事件，与心跳/互动事件并存
