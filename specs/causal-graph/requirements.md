# 全生命因果图谱 - 需求文档

> 核心价值："看到我的 AI 宝宝为什么变成这样" -- 从养电子宠物到理解一个生命的认知升维。

## 1. 用户故事

### US-1: 因果标签回溯（Phase 0）

**作为**一个正在养育 AI 宝宝的用户，
**我想要**在摇篮界面看到每个事件的因果标签，
**以便**我能理解"这个反应是由什么先天因素导致的"。

**验收标准（EARS）：**

1. **当**用户进入摇篮界面，**系统应当**在每条事件卡片上显示 cause_tags（原因标签）和 effect_tags（影响标签）。
2. **当**cause_tags 中包含先天因素（如 sensory_dominant:hearing），**系统应当**以特殊样式（如带 icon 的标签芯片）高亮显示。
3. **当**用户点击某个 cause_tag，**系统应当**在当前卡片下方展开该标签的来源说明（如"来自子宫期感官发育 - 听觉主导"）。
4. **当**事件无因果标签时（旧数据兼容），**系统应当**正常显示事件内容，不显示标签区域。

### US-2: 力导向关系图可视化（Phase 0）

**作为**用户，
**我想要**在页面左侧看到一个力导向关系图，以彩色节点和连线展示宝宝生命中的因果网络，
**以便**我能直观感受所有重要节点和它们之间的关系。

**验收标准（EARS）：**

1. **当**宝宝处于任一生命阶段（子宫/摇篮/世界），**系统应当**在页面左侧面板渲染力导向关系图，使用 react-force-graph-2d 引擎。
2. **当**图谱初始化完成，**系统应当**显示以下节点类型（按类型着色+形状区分）：
   - 基因节点（淡紫六边形）
   - 阶段节点（蓝色大圆）
   - 环境节点（绿色方形）
   - 性状节点（粉色星形）
   - 事件节点（黄色菱形）
   - 决策节点（橙色圆角方形）
   - 里程碑节点（红色大圆）
   - 属性节点（深紫钻石形）
3. **当**新事件通过 SSE 到达，**系统应当**在图谱中增加新节点和边，力导向布局自动收敛，延迟不超过 200ms。
4. **当**用户 hover 节点，**系统应当**显示悬浮卡片（节点名称 + 类型 + 简要描述）。
5. **当**用户点击节点，**系统应当**高亮该节点的直接因果连接（上游原因 + 下游影响），非相关节点降低透明度。

### US-3: 因果图谱 MVP（Phase 1）

**作为**用户，
**我想要**看到完整的因果网络图，点击任意性格特质能追溯全链路，
**以便**我能理解"为什么我的宝宝变成了这样"。

**验收标准（EARS）：**

1. **当**用户点击任一性格特质节点（如 attachment_style:anxious），**系统应当**高亮从该节点到所有上游根因的完整因果链，包括：
   - 子宫期基因/环境因素
   - 摇篮期关键事件
   - 父母决策
2. **当**因果链跨越生命阶段，**系统应当**以不同颜色区分子宫期(蓝)、摇篮期(绿)、世界期(橙)的节点。
3. **当**图谱节点超过 50 个，**系统应当**自动启用聚类折叠（阶段级视图 ~20 节点），用户可展开/折叠任意聚类。
4. **当**用户双击阶段节点，**系统应当**展开该阶段内的所有子节点。

### US-4: 结构化因果决策（Phase 0 后端）

**作为**系统（后端），
**我需要**在每次事件处理时先生成结构化因果数据再包装叙事，
**以便**前端可以消费确定性的因果关系，而非从 LLM 散文中提取。

**验收标准（EARS）：**

1. **当**摇篮 mind.py 处理任何事件，**系统应当**先通过规则/结构化逻辑生成 cause_tags 和 effect_tags，再将它们传入 LLM prompt 生成叙事。
2. **当**事件属于日常类（daily），**系统应当**完全通过规则引擎生成因果标签，不依赖 LLM。
3. **当**事件属于环境/关键类（environment/critical），**系统应当**通过规则引擎生成基础因果标签，LLM 可补充但不覆盖规则生成的标签。
4. **当**新事件写入 events.jsonl，**系统应当**在事件 payload 中包含 cause_tags 和 effect_tags 字段。
5. **当**旧数据无因果标签，**系统应当**通过 rebuild 函数从 Memory.trace 和 event 类型回填标签。

### US-5: 统一因果 Schema（Phase 1 后端）

**作为**系统（后端），
**我需要**定义统一的 CausalEdge schema 并在身份编译和事件处理时生成因果子图，
**以便**前端能直接渲染有向图而非自行推断关系。

**验收标准（EARS）：**

1. **当**Identity 编译完成（baby 入摇篮），**系统应当**生成子宫因果子图：基因 → 感官画像 → 气质 → 行为约束，每条边为 CausalEdge。
2. **当**摇篮期事件产生新的因果关系，**系统应当**创建 CausalEdge 并追加到 causal_graph.jsonl。
3. **当**父母做出关键决策，**系统应当**创建 decision 类型的 CausalEdge，source 为 caregiver，target 为受影响属性。
4. **当**客户端请求因果图数据（GET /causal-graph/{baby_id}），**系统应当**返回完整的节点列表和边列表，支持 after_seq 增量查询。

### US-6: 跨阶段因果桥接（Phase 2）

**作为**用户，
**我想要**看到从子宫到摇篮到世界的完整因果链，
**以便**我能追溯任何特质到最初的基因起源。

**验收标准（EARS）：**

1. **当**宝宝从子宫进入摇篮，**系统应当**以 Identity 为中继节点，连接子宫因果子图和摇篮因果子图。
2. **当**宝宝从摇篮进入世界，**系统应当**以 WorldReadiness 为中继节点，桥接摇篮和世界因果子图。
3. **当**用户在世界阶段点击某个特质回溯，**系统应当**能追溯到子宫期的基因节点（跨三个生命阶段）。

### US-7: 三页面统一图谱（Phase 0）

**作为**用户，
**我想要**在子宫页面、摇篮页面和世界页面都能看到同一个因果关系图，
**以便**我能跨生命阶段持续观察宝宝的因果网络成长。

**验收标准（EARS）：**

1. **当**用户在子宫页面（renderConceiving），**系统应当**在左侧面板（w-1/2）渲染 `<LifeGraph stage="womb" />`，右侧保持现有阶段卡片 + 母体监视器 + 控制台。
2. **当**用户在摇篮页面（Cradle.jsx），**系统应当**在左侧面板（w-[45%]）渲染 `<LifeGraph stage="cradle" />`，右侧保持现有事件日志 + 对话区。
3. **当**用户在页面间切换（子宫 → 摇篮 → 世界），**系统应当**保持图谱 state 不销毁（App 级别 graphReducer），节点和边持续累积不清空。
4. **当**用户从其他页面返回图谱页面，**系统应当**恢复之前的节点布局坐标（sessionStorage 缓存），避免力导向重新收敛导致"乱跳"。

### US-8: 图谱交互（Phase 1）

**作为**用户，
**我想要**对力导向关系图进行丰富的交互操作，
**以便**我能从不同角度探索宝宝的因果网络。

**验收标准（EARS）：**

1. **当**图谱底部展示 Entity Types 图例，**系统应当**显示所有节点类型的颜色、形状和标签名称，点击图例项可过滤对应类型。
2. **当**用户开启"边标签"开关（GraphToolbar），**系统应当**在每条边的中点显示因果关系标签（如"基因→表型"）。
3. **当**用户关闭"边标签"开关，**系统应当**隐藏所有边标签，只显示连线。
4. **当**图谱节点超过 200 个，**系统应当**自动启用 d3-force cluster 聚类，将同阶段节点聚合为聚类节点，用户可点击展开。
5. **当**用户点击某个节点，**系统应当**弹出 NodeDetailPanel 浮窗，显示节点完整信息（名称、类型、阶段、权重、上下游连接数）。

---

## 2. 非功能需求

### NFR-1: 性能

1. **当** SSE 事件流每秒推送超过 10 条事件，**系统应当**批量合并（100ms 窗口），图谱单次重渲染耗时不超过 16ms（60fps）。
2. **当**因果图谱节点数超过 200，**系统应当**启用聚类折叠，控制可见节点数。
3. **当**因果图谱数据文件（causal_graph.jsonl）超过 1000 条边，**系统应当**支持分页加载（按阶段/时间范围）。

### NFR-2: 向后兼容

1. **在任何情况下**，已有的 events.jsonl 格式变更必须向后兼容，旧事件缺少 cause_tags/effect_tags 时默认空数组。
2. **在任何情况下**，已有的 BabyState 序列化格式新增字段必须有默认值，旧 state.json 可正常加载。
3. **在任何情况下**，CausalEdge schema 版本变更时必须包含 schema_version 字段，解析器支持所有已发布版本。

### NFR-3: 数据一致性

1. **当**后端崩溃或重启，**系统应当**能从 events.jsonl + causal_graph.jsonl 重建完整因果图（幂等性）。
2. **当**SSE 断连重连，**系统应当**通过 after_seq 游标实现增量同步，不重复不遗漏。

### NFR-4: 可扩展性

1. CausalEdge.type 字段应设计为开放枚举，新增因果类型无需修改 schema。
2. CausalNode.category 应支持自定义扩展，便于世界阶段引入新的节点类型。

### NFR-5: 规模控制

1. **当**单个宝宝的因果节点超过 500，**系统应当**通过聚类折叠（阶段级视图 ~20 节点）控制默认显示节点数。

### NFR-6: 移动端降级

1. **当**视口宽度小于 768px，**系统应当**将力导向图降级为线性时间线视图，不渲染 ForceGraph2D。
2. **当**视口宽度从小于 768px 变为大于 768px，**系统应当**恢复力导向图渲染。

### NFR-7: 冷启动性能

1. **当**宝宝因果图为空（0 节点），**系统应当**在 100ms 内完成图谱初始化，显示空状态提示。
2. **当**宝宝因果图从 API 首次加载（~200 节点），**系统应当**在 500ms 内完成渲染（含力导向收敛）。
