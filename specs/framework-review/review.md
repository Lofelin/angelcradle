# 框架调研报告审查意见

> 审查日期: 2026-04-13
> 审查对象: Agent B 提出的 11 条优化建议
> 项目阶段: 早期产品验证期，核心玩法迭代中，用户量 ~1

## 审查总原则

三问过滤：
1. **真实需求还是臆想？** — 当前单用户、单进程、本地开发，大部分"性能优化"和"生产加固"都是臆想需求。
2. **有更简单的方案吗？** — 早期验证期的唯一目标是快速验证玩法，任何不直接服务于此的改动都是成本。
3. **会破坏什么？** — 重构和迁移有引入新 bug 的风险，打断开发节奏的隐性代价远大于表面投入时间。

---

## 逐条审查

### 1. 安装 uvloop + httptools（报告 P0）

**判定: 不做**

- **收益**: 事件循环性能 ~2x。但 2x of what？当前瓶颈是 LLM API 调用（单次 2-10 秒），不是事件循环。即使事件循环快 10x，用户体感为零。
- **风险**: uvloop 仅支持 Linux/macOS，开发环境若有 Windows 协作者会出问题。httptools 偶尔与某些 ASGI 中间件有兼容性问题。
- **结论**: 典型的"数字好看但体感为零"优化。单用户场景下，事件循环根本不是瓶颈。

### 2. gunicorn + uvicorn workers（报告 P0）

**判定: 不做**

- **收益**: 进程管理 + 崩溃恢复。但当前是 `python main.py` 本地开发，没有生产部署场景。
- **风险**: 多 worker 模式下，内存中的 DES 调度器状态无法跨进程共享，会直接导致架构崩塌。当前架构是单进程内存状态模型，多 worker 是矛盾的。
- **关键问题**: 如果真的上多 worker，scheduler.py 的全局状态、baby lock、heapq 队列全部失效。这不是"配置一下"的事，是架构重设计。
- **结论**: 不仅不值得做，在当前架构下做了会出严重问题。等有真实部署需求时再考虑，届时需要先解决状态管理问题。

### 3. 收窄 CORS 配置（报告 P0）

**判定: 延后（产品验证通过后做）**

- **收益**: 安全加固。但 `allow_origins` 已经限定了 `localhost:5173` 和 `localhost:3000`，并非完全开放。`allow_methods=["*"]` 在仅有 GET/POST 的 API 上影响微乎其微。
- **风险**: 改动量极小（一行），但如果改错可能导致前端请求被拦截，调试起来浪费时间。
- **结论**: 这是一个 30 秒的改动，但在没有公网暴露的本地开发阶段，收益为零。等部署到公网前再收窄。

### 4. LLM 客户端迁移到 async SDK（报告 P1）

**判定: 不做**

- **收益**: 消除 `asyncio.to_thread` 开销。但 `to_thread` 的开销是微秒级，LLM 调用是秒级。overhead 占比 < 0.01%。
- **风险**: 需要修改 llm.py 核心调用链 + 所有 6+ 处 `asyncio.to_thread` 调用点 + 测试验证。影响面广，容易引入回归 bug。
- **隐性成本**: 同步 SDK 的好处是调试简单、stack trace 清晰。async SDK 的异常追踪更复杂，对早期调试不友好。
- **依赖关系**: 如果迁移，womb/ 和 cradle/ 的所有 LLM 调用模式都要改，这是全局性重构。
- **结论**: 收益不可感知，风险和工作量实实在在。等产品稳定后，如果需要支持高并发再考虑。

### 5. scheduler.py 拆分（报告 P1）

**判定: 现在做**

- **收益**: 1522 行的文件确实超出合理范围（项目规范 800 行上限）。阅读和维护成本高，每次修改都需要在巨大文件中导航。
- **风险**: 纯结构重构，不改逻辑，风险可控。拆分为 core/handlers/naming/config 是合理的边界。
- **关键理由**: scheduler.py 是当前迭代最频繁的文件（核心玩法都在这里调），大文件直接拖慢开发速度。这个改动直接服务于"快速迭代"的目标。
- **结论**: 唯一一条真正服务于当前开发效率的建议。建议执行，但拆分方案需要仔细设计，确保模块边界清晰。

### 6. registry.py 加文件锁（报告 P2）

**判定: 不做**

- **收益**: 保护并发写入。但 registry.py 仅 46 行，写入操作只在"孕育完成"时触发（低频，一次一个）。
- **风险**: 引入 filelock 依赖，增加复杂度。在单用户单进程场景下，不存在并发写入问题。
- **结论**: 解决一个不存在的问题。

### 7. 引入 json-repair 库替代手写修复（报告 P2）

**判定: 延后（产品验证通过后做）**

- **收益**: 当前 `parse_json` 约 110 行（含状态机），json-repair 库更成熟更全面。
- **风险**: 手写的修复逻辑是针对当前 LLM 实际输出模式的（bracket balancing、inner quote escaping），已经在线上跑通。换库可能引入边缘 case 回归。
- **关键考量**: 如果当前 parse_json 频繁失败，才有替换的紧迫性。如果它工作良好，"更优雅"不是理由。
- **结论**: 如果当前修复逻辑经常失败，立即做；如果工作良好，等稳定后再替换。

### 8. 添加 slowapi 速率限制（报告 P2）

**判定: 不做**

- **收益**: 保护 LLM 调用端点。但用户就是开发者自己，不存在恶意调用。
- **风险**: 速率限制可能在调试时误触，反而阻碍开发。
- **结论**: 解决一个不存在的威胁。等有真实用户时再加。

### 9. SSE 迁移到 sse-starlette（报告 P2）

**判定: 延后（产品验证通过后做）**

- **收益**: 规范化 SSE 实现 + 自动 ping 保活。当前使用 5 处 `StreamingResponse` 手写 SSE。
- **风险**: 需要改动所有 SSE 端点的生成器逻辑，测试成本不低。
- **关键考量**: 如果当前 SSE 连接有断连问题（nginx/proxy 超时断开），sse-starlette 的自动 ping 有实际价值。如果没有断连问题，优先级很低。
- **结论**: 当前本地开发不走 proxy，断连问题不存在。等部署到有 proxy 的环境时再做。

### 10. SQLite 持久化层（报告 P3）

**判定: 延后（产品验证通过后做）**

- **收益**: 事务性、查询能力、并发安全。
- **风险**: 这是架构级迁移，影响 state.py、registry.py、events 日志、所有读写逻辑。工作量巨大。
- **关键考量**: 当前文件系统持久化（JSON/JSONL）在单用户场景下工作良好，简单直观，调试时直接打开文件就能看数据。这是早期验证的巨大优势。
- **结论**: 文件系统是早期验证的最佳选择。等需要多用户 / 复杂查询 / 事务保障时再迁移。

### 11. 结构化日志（报告 P3）

**判定: 延后（产品验证通过后做）**

- **收益**: JSON 日志便于 grep 和聚合分析。
- **风险**: 人类可读性下降，调试时需要额外工具解析。
- **结论**: 当前阶段开发者直接看控制台日志，人类可读的 basicConfig 反而更高效。等有日志聚合系统（ELK/Loki）时再做。

## 总结

11 条建议中，10 条在当前阶段都是过度工程化。唯一值得立即做的是 scheduler.py 拆分——它直接服务于开发效率，而不是解决假想的性能/安全问题。

Agent B 的报告犯了一个典型错误：用生产级思维审视原型期项目。早期验证期的核心矛盾是"玩法是否成立"，不是"系统是否健壮"。在玩法验证通过之前，每一分钟花在基础设施上的时间都是从产品验证中偷走的。

> 永远先写最简单能运行的实现，再考虑扩展。
