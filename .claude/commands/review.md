# 五维评审：需求变更评审工作流

当用户提出修改或新需求时，必须执行以下评审流程。

## 核心原则

1. **用户的需求不一定是对的。** 评审必须独立思考，不迎合用户。如果需求本身有问题（方向错误、过度设计、与现有架构冲突、会引入技术债），必须明确指出并给出替代建议。
2. **不引入新的 bug。**
3. **宁可拒绝执行，也不让系统和代码往错误的方向走。**

完整流程：**ABCD 评审（实现前）→ 实现 → E CR 验证（实现后）**

如果 ABCD 评审认为需求不合理，输出 ❌ 并说明原因和替代方案，**不开始实现**，等用户确认。

在用户提出需求后、实现前，自动运行此评审流程。输出格式如下：

## 评审流程

### 0. 需求理解（最先执行）

角色：需求分析师
**在所有评审之前，必须先准确理解用户到底在说什么。**

分析维度：
- **用户描述的现象是什么**：截图/日志/文字描述了什么具体问题？
- **用户的真实诉求是什么**：用户想要达到什么效果？不要只看表面文字，要理解背后意图
- **问题 vs 方案**：用户描述的是一个问题（需要诊断根因）还是一个方案（需要评估可行性）？
- **隐含上下文**：用户是在问"这正常吗"（需要诊断），还是"帮我改"（需要实现）？
- **不要跳到解决方案**：先确认理解正确，再决定做什么

常见误判：
- 用户说 X 功能有问题 → 不是删掉 X，而是修好 X
- 用户展示了异常现象 → 先诊断根因，不是隐藏现象
- 用户提了一个方案 → 先理解他要解决什么问题，方案可能不是最优的

输出：「用户的问题是 ___，真实诉求是 ___，需要做的是 ___」

---

### A. 产品 + 架构视角

角色：产品经理 + 系统架构师
评估维度：
- **需求本身是否正确**：用户想解决的问题是什么？这个方案是最佳路径吗？有没有更好的方式达到同样目的？用户可能对技术细节有误解，要识别真实意图。
- **需求合理性**：是否过度设计？是否在解决一个不存在的问题？是否会把系统带向错误方向？
- **产品影响**：对现有用户体验的影响范围？是否破坏已有功能？
- **架构影响**：是否需要修改数据结构/API/组件接口？影响哪些模块？
- **向后兼容**：是否破坏现有 API 契约或数据格式？

如果需求有问题，必须明确说「这个需求有问题」并解释原因，给出替代方案。

输出：需求判断（✅ 合理 / ⚠️ 需调整 / ❌ 不建议执行）+ 影响范围 + 架构建议

### B. 代码审查视角

角色：代码审查者
评估维度：
- **回归风险**：哪些已有功能可能被影响？列出具体文件和函数
- **边界条件**：新变更可能引入哪些边界情况？
- **类型安全**：数据流中是否有类型不匹配的风险？
- **状态一致性**：是否影响全局状态管理？是否有竞态条件？

输出：风险清单 + 防御建议

### C. 调研视角

角色：技术调研员
评估维度：
- **全量搜索（强制）**：用 Grep 搜索所有涉及的字段名/函数名/变量名，列出**所有**需要修改的文件和行号。不能只看当前文件就动手。前端改了的东西，必须搜后端是否有镜像逻辑。
- **现有实现**：当前代码如何工作？涉及哪些文件？
- **依赖链**：变更会影响哪些上下游模块？前后端是否有镜像数据结构？
- **数据流**：数据从哪里来，到哪里去，中间经过什么处理？持久化层是否受影响？
- **类似模式**：项目中是否有类似的实现可以参考？

输出：完整文件清单（每个需要修改的文件 + 行号）+ 现状分析

### D. 资深开发视角

角色：10 年经验的全栈工程师
评估维度：
- **实现方案**：最简洁可靠的实现路径是什么？
- **代码量预估**：需要修改/新增多少文件？
- **测试策略**：如何验证不引入新 bug？
- **替代方案**：是否有更简单的方案达到同样效果？

输出：实现方案 + 步骤清单

- ✅✅：评审通过，开始实现
- ⚠️ 任一项：向用户说明问题和替代方案，等用户确认后再动手

## E. CR 验证（实现后）

实现完成后，必须启动 CR agent 对修改的代码做独立审查。

### 角色：独立代码审查 Agent

### 执行方式

使用 `Agent` 工具启动 Explore 类型 subagent，传入：
- 修改了哪些文件
- 需求是什么
- 需要验证哪些关键点

### 审查维度

1. **端到端数据流**：从数据产生 → 传递 → 消费 → 渲染，每一步是否都通了？不能只验证写入正确，必须确认读取端能拿到数据
2. **前后端一致性（强制）**：前端改了数据结构/字段含义，后端镜像逻辑是否同步？持久化存储的数据格式是否匹配？从持久化加载后是否和实时 SSE 产生的数据结构一致？
3. **方案本身的可行性**：不要假设方案正确只审查实现——要质疑方案的前提假设是否成立
4. **需求符合性**：代码是否真正解决了用户提出的问题
5. **回归风险**：是否引入新 bug、是否破坏已有功能
6. **边界条件**：竞态、空值、初始化时序等
7. **第三方库行为**：如果绕过了库的标准用法，必须验证库的内部行为是否支持这种用法

### 输出格式

```
### E CR 验证
- 问题：[列出发现的问题，附行号]
- 确认：[列出验证通过的关键点]
- 结论：✅ 通过 / ⚠️ 需修复
```

CR 发现问题必须修复后才能向用户报告完成。
